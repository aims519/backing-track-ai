# 0040. TestFlight upload on every push to main, with plain `xcodebuild` and cloud signing

Status: Accepted

## Context

Until now the app reached a phone by running it from Xcode. That's the "no App Store
distribution for MVP" position in
[`docs/backing-track-generator-scope.md`](../backing-track-generator-scope.md). With the paid
Apple Developer membership in place for push notifications
([ADR 0039](0039-apns-push-from-api-on-terminal-job-state.md)), TestFlight became available. It
gives installs that last 90 days instead of a development build that needs reinstalling, plus
production APNs tokens that match the Pi's Production APNs config.

A first build was uploaded by hand through Xcode Organizer, which proved the app record, signing
and push entitlement all work. The goal here is to make that repeatable: numbered builds that
come from a known commit, without a hand-run archive each time.

Several past bugs only showed up on a physical device and never in the Simulator: sampler
voice stealing, and Now Playing / audio-session behaviour. So having main's current build on the
phone is worth more than it would be for an app whose Simulator runs are representative.

Constraints already in place:

- CI runs on a self-hosted Mac, because GitHub-hosted macOS minutes bill at 10x on a private
  repo (`ios-ci.yml`).
- The `.xcodeproj` is generated by XcodeGen and not committed
  ([ADR 0019](0019-xcodegen-over-committed-xcodeproj.md)).
- The team ID and the Pi's API URL live in a gitignored `Config/Local.xcconfig`.

## Decision

**A GitHub Actions workflow (`ios-release.yml`) on the self-hosted runner archives the app and
uploads it to TestFlight with plain `xcodebuild` on every push to `main` that touches `app/`.**

- **Trigger:** push to `main`, path-filtered to `app/**`. This is the iOS counterpart of
  `deploy.yml` for the API. The internal TestFlight group has automatic distribution on, so each
  upload reaches the phone once Apple has processed it. The workflow first calls `ios-ci.yml`
  (now a `workflow_call` target instead of also triggering on push to `main`), so the SHA is
  built and tested before it's archived. This mirrors how `deploy.yml` calls `verify.yml`.
- **Numbering:** `MARKETING_VERSION` stays in `project.yml` and is bumped by a commit when a
  change deserves a new version number. `CURRENT_PROJECT_VERSION` is `github.run_number + 100`,
  passed to `xcodebuild` as an override so nothing is committed back. The offset keeps CI build
  numbers above those uploaded by hand before the workflow existed.
- **Signing:** automatic signing with an App Store Connect API key (`-allowProvisioningUpdates`
  with `-authenticationKey*`). Apple creates and holds the distribution certificate ("cloud
  signing"), so no `.p12` or provisioning profile goes into secrets or the runner's keychain.
- **Upload:** `xcodebuild -exportArchive` with `destination: upload` in
  `app/Config/ExportOptions.plist`, the same thing Organizer's "Distribute App → App Store
  Connect" does. No altool or Transporter step.
- **Per-machine config:** the team ID and the API URL come from repo variables
  (`IOS_DEVELOPMENT_TEAM`, `IOS_API_BASE_URL`) as command-line build settings. The workflow
  fails before archiving if either is missing, because a Release build without an API URL only
  fails at launch, on the phone.
- **Export compliance:** `ITSAppUsesNonExemptEncryption = NO` in `project.yml`. Otherwise every
  build would stop at "Missing Compliance" and automatic distribution would never happen.

## Alternatives considered

**Tag-triggered releases** (push `ios-vX.Y.Z` to archive and upload, with the version taken
from the tag). This was the first design and was dropped. It makes every build a deliberate act
and gives version numbers meaning, which matters when builds go to people outside the team.
Here the only tester is the owner, and the useful thing is main on the device without asking
for it. A tag trigger is the natural addition if external testers or App Store submission
arrive: continuous internal builds, plus deliberate tagged releases for anything outside the
team.

**fastlane (`gym` + `pilot`, with `match` for certificates).** Rejected. It adds a Ruby
toolchain and a Gemfile to a repo that has neither. `match` also needs a separate encrypted
certificates repo. Cloud signing through an API key makes that unnecessary for a single-team,
single-app project. The two `xcodebuild` calls fastlane would wrap are short enough to read
directly in the workflow.

**Xcode Cloud.** Rejected, after one was set up by accident and then removed. It would
put a second CI system, configured in App Store Connect rather than in the repo, next to the
GitHub Actions setup for the API. It can't generate the project without adding a
`ci_scripts/ci_post_clone.sh` to run XcodeGen. The per-machine config would also need to live in
Xcode Cloud's own environment variables. Its free compute allowance was not the deciding factor.

**GitHub-hosted macOS runners.** Rejected for the same billing reason as `ios-ci.yml`.

**Manually managed certificates** (export a `.p12` and profile into secrets, import them into a
temporary keychain each run). Rejected. It means more secrets that expire yearly, plus keychain
scripting that cloud signing makes unnecessary.

**`git rev-list --count HEAD` as the build number.** It's reproducible from the SHA, but App
Store Connect rejects a re-run of the same commit as a duplicate. The run number always
increases, and is fine for a build number nobody reads.

## Consequences

- Every `app/` change merged to `main` ends up on the phone with no manual step. The price is
  a TestFlight update for each merge, including trivial ones. Changes outside `app/`, such as
  docs or the API, don't trigger it.
- It only works while the self-hosted Mac is on and running the runner. A push while it's off
  waits in the queue rather than being lost.
- Forgetting to bump `MARKETING_VERSION` is harmless: builds keep going under the same version
  with increasing build numbers. The version only changes when someone decides it should.
- The API key has the Admin role, which cloud-managed distribution certificates require. That's
  broader than an upload-only key, and it covers the whole team, not just this app. It's
  stored only as a repo secret and named for its one consumer, so it can be revoked without
  affecting anything else.
- The archive step signs with a development identity before export re-signs it for
  distribution. On this self-hosted Mac that comes from the owner's login keychain, so the
  runner depends on that keychain being available to the launchd-run service. The runner's
  LaunchAgent plist had `SessionCreate = true` (the default in GitHub's `svc.sh` template),
  which gives jobs a fresh security session where the login keychain is locked, so `codesign`
  failed with `errSecInternalComponent`. The key was removed, so jobs run in the logged-in GUI
  session, where the keychain is already unlocked. Two costs follow. Every job on the runner,
  including PR runs of `ios-ci.yml`, can use that unlocked keychain. And reinstalling the
  runner with `svc.sh install` puts the key back and breaks signing again. The rejected
  alternative was unlocking the keychain in the workflow, which needs the Mac login password
  stored as a GitHub secret. A clean, ephemeral runner would need a dedicated CI keychain
  instead.
- Build numbers aren't reproducible from a commit: re-running the workflow produces a new,
  higher build number. This is intended, because a re-run is a new upload.
- The scope doc's "no App Store distribution" non-goal still holds for the public App Store,
  but builds now reach TestFlight. Internal testing needs no Beta App Review, so ATS being
  disabled ([ADR 0022](0022-plaintext-http-over-tailscale-ats-disabled.md)) doesn't block this.
  Inviting external testers would trigger that review.
